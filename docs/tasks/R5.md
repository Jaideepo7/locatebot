# R5 — Live Photon + Telegram test (people, with an agent helping)

Not a coding task: a checklist for the team, run after R2 and R3 are merged and with internet allowed (roadmap decision D5). An agent can drive the terminal steps and write the results; a person handles the Photon dashboard and the phone.

## Before
- Photon project created; Telegram bot connected (Photon dashboard or `POST /v1/projects/{id}/platforms/telegram/bots`); API key `pho_sk_...`, project id `pho_prj_...` in the Pi's `.env` (git-ignored). WebSocket delivery enabled if the project needs a setting for it.
- Pi: `tools/remote_run.py --robot zmq --orin-host <orin>` running; Orin: `tools/orin_run.py --pi-host <pi>` running (simulated room acceptable for the first pass: `--sim` on the Orin side if the car isn't ready).

## Steps (record pass/fail, times and screenshots in `docs/remote/LIVE-TEST.md`, no personal data)
1. `/help` → reply within 5 s.
2. `/find marker` → replies: accepted, searching, (detected, approaching, completed) or not-found; each matches what the Orin page shows.
3. `/status` mid-search → current state; `/cancel` → cancelled and the car stops.
4. Second `/find` while busy → "already searching", not queued.
5. Another Telegram account `/cancel` → refused (ownership).
6. Pull the Pi's internet for 60 s mid-mission → robot unaffected; replies arrive after reconnect, none duplicated (outbox idempotency).
7. Restart `remote_run.py` mid-mission → no duplicate replies; state recovers.
8. Capture one real inbound event, strip personal data, replace `tests/fixtures/photon_message_received.json`; confirm `senderId` (bot user from `receivedBy`) and that `format: "plain"` works for Telegram (open questions from the original branch).
9. Measure: message → robot start latency; RSS of `remote_run.py` on the Pi over 30 min.
