## What to build
1. **`locatebot/remote/photon_ws.py`**: `PhotonWebSocketInbound(api_key, project_id, on_message, store, clock=..., connect=...)`.
   - Outbound connection from the Pi; authentication exactly as documented; key from `PHOTON_API_KEY` (never logged; scrub it from exceptions).
   - For each event: the **same** parsing as the webhook path (`photon.parse_event`), dedupe by Photon's event id in the SQLite store (same table the webhook path uses), then `on_message(InboundMessage)`; acknowledge if the protocol requires it, *after* the store commit.
   - Heartbeats/ping per the docs; reconnect with exponential backoff and jitter (1 s → 30 s cap); resume/replay semantics per the docs; never crash the process on a bad frame (count and log it).
   - Runs in its own thread with its own asyncio loop (the rest of the service is threaded); `start()`, `stop()` (prompt, closes the socket), `status()` (connected, last event time, reconnects, dropped frames).
   - Injectable `connect` so tests use a local fake server.
2. **`config.py`**: `PHOTON_INBOUND=websocket|webhook` (default `websocket`); webhook-only settings required only in webhook mode.
3. **`tools/remote_run.py`** (runs on the Pi): loads `.env`/environment, builds `RemoteService` (R1), starts the inbound mode, the local operator HTTP server (bind host/port flags, default 127.0.0.1:8070), the outbox sender; robot link `--robot fake` for now (R3 adds `--robot zmq`); `--console` to print replies instead of sending; Ctrl+C/SIGTERM clean shutdown; prints RSS every 60 s at debug level.
4. **Offline behaviour:** when the internet/Photon is down, the robot is unaffected; inbound reconnects quietly; replies stay queued in the outbox (already durable) and send later; `/healthz` shows `photon_connected: false`.
5. **Docs:** extend `docs/remote/README.md`: WebSocket mode, how to run on the Pi (`tools/remote_run.py`), systemd unit example (`deploy/locatebot-remote.service`, `MemoryMax=150M`, restart always), measured RSS, what still needs a live test (R5).
